# FaultInjection

## 演练目标
通过混沌工程（Chaos Engineering）手段，验证系统在关键基础设施或外部依赖失效时的容错与降级能力。

## 演练场景记录

### 场景 1：Redis 集群部分节点宕机
- **故障注入方式**: 使用 `iptables` 丢弃 Redis 集群中某一个主节点的所有出入站数据包，模拟网络隔离/节点宕机。
- **系统表现**:
  - Live Access Service 的 Redis 客户端抛出连接超时异常。
  - 系统回源至 MySQL 进行权益校验。
  - 网关层的 `AdmissionRateLimiter`（基于 Redis 的限流器）发生降级，部分超出阈值的流量触发了本地保护机制。
- **恢复时间**: 约 15 秒后，Redis 哨兵/集群机制完成主从切换，系统自动恢复为缓存读取。
- **是否满足目标**: **部分满足**。虽然主从切换成功，但 15 秒的回源洪峰导致 MySQL QPS 飙升至 8,000，存在一定风险。后续考虑增加“数据库并发回源上限”保护。

### 场景 2：外部视频云提供商全面瘫痪
- **故障注入方式**: 在网关出口侧，通过代理拦截发往视频云 API 的所有请求，并强制返回 HTTP 502。
- **系统表现**:
  - 前 200ms 内，请求因超时挂起。
  - 随后断路器迅速跳闸（OPEN 状态）。
  - 所有新进入直播间的请求被快速拦截，返回友好的降级页面。
  - 已经获取过 Token、正在通过 CDN 拉流的学生**完全未受影响**。
- **恢复时间**: 撤销注入后，1 分钟内断路器通过半开探测恢复闭合。
- **是否满足目标**: **满足**。完美实现了可用性隔离（QAS-003）。

### 场景 3：消息队列 (MQ) 代理节点崩溃
- **故障注入方式**: 强制停止 RabbitMQ 容器。
- **系统表现**:
  - Order Service 在支付回调后无法发布 `OrderPaidEvent`，本地事务回滚？（注：当前架构中支付状态已先落库）。
  - 根据设计，Order Service 会捕获发信异常，但如果仅仅捕获，事件将丢失。
- **改进发现**: 演练暴露了当前设计的缺陷。支付状态推进和 MQ 发布不是原子的。
- **行动项**: 必须引入**本地消息表 (Outbox Pattern)**。在更新订单为 PAID 的同一个本地事务中，写入一张 Event 表。定时任务扫描该表投递 MQ，彻底保证 100% 可靠投递。
