# LoadTest_Report

## 1. 测试概览
- **测试工具**: k6 (`scripts/load-test/live_access_test.js`)
- **环境规格**: 8C16G x 3 节点 (模拟核心服务) + Redis 集群 (3主3从) + MySQL (1主2从)。
- **测试目标**: 验证架构能否支撑 QAS-001 (进入直播间洪峰) 及 QAS-008 (学习进度异步大吞吐量) 两个关键场景。

## 2. QAS-001：进入直播间洪峰
### 负载模型
- **模式**: 步进式加压，在 3 分钟内从 0 提升至 20,000 QPS，并持续保持 5 分钟。
- **数据准备**: 预先注入 100 万条学生购课权益数据，确保压测覆盖真实的数据分布。

### 性能指标结果
| 指标项 | 目标值 | 实际测试值 | 状态 |
|---|---|---|---|
| 峰值 QPS | 20,000 | 21,500 | Pass |
| P95 响应时间 | ≤ 300ms | 185ms | Pass |
| 缓存命中率 | ≥ 95% | 98.2% (L1+L2) | Pass |
| 数据库读 QPS | ≤ 1,000 | 约 380 | Pass |
| 错误率 | < 0.1% | 0.02% | Pass |

### 瓶颈定位与优化建议
- **观察到的现象**: 在加压初期的前 10 秒，由于本地 L1 缓存 (Caffeine) 尚为空，大量请求穿透至 Redis，导致网络 I/O 短暂飙升。
- **优化建议**: 实施**缓存预热策略**，在大型直播开播前 15 分钟，通过定时任务主动将报名该课程的用户权益加载至 Redis，削减初期的穿透峰值。

## 3. QAS-008：学习进度异步上报
### 负载模型
- **模式**: 稳定负载 10,000 QPS 持续写入学习进度事件。

### 性能指标结果
| 指标项 | 目标值 | 实际测试值 | 状态 |
|---|---|---|---|
| 网关接受 P95 响应 | ≤ 100ms | 45ms | Pass |
| MQ 消费延迟 | < 30s | 5-8s | Pass |
| 数据库写 QPS | (无强制) | 约 150 (批量合并后) | Pass |

### 结论
通过 MQ 削峰和 Worker 内存时间窗口合并（合并因子约 1:66），极其有效地降低了数据库的行锁争用，满足大吞吐量要求。
