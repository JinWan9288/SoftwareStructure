### ADR-002：进入直播间采用“直连数据库与第三方视频云同步校验”

---

> **状态:** Deprecated (已被 ADR-002a 替代) 
> **日期:** 2025-11-12
> **关联场景:** -
> **关联模块**: 直播接入服务，缓存集群
>
> ---

#### 1. 背景 (Context)
在平台建设初期（MVP 验证阶段），首要任务是快速跑通“购课-上课”的核心业务闭环。由于当时平台日活用户较少，没有集中性的大流量洪峰，系统架构侧重于实现的简单性与业务逻辑的绝对正确性，暂未将高并发防御与外部依赖隔离作为首要考量。

#### 2. 决策 (Decision)
当学生点击“进入直播间”时，系统采用最直接的串行同步处理模型：
1. **同步查库**：Web 线程直接执行 SQL 查询底层的关系型数据库，校验学生是否真实拥有该课程权益。
2. **同步调用外部 API**：若权限校验通过，当前线程继续通过 HTTP Client 同步调用第三方视频云 API，实时获取底层的防盗链推拉流地址。
3. **组装返回**：等待外部 API 响应后，将数据组装返回给前端播放器。

#### 3. 后果 (Consequences)
* **收益**：开发极速，逻辑极其直观；具备绝对的数据强一致性（例如：用户发起退款的下一秒，就绝对无法再进入直播间）。
* **代价**：系统的吞吐量上限（TPS/QPS）被底层数据库的读并发能力和外部第三方 API 的网络 I/O 耗时严重锁死。

#### 4. 废弃原因 (Reasons)
在应对开学季“万人同时开课”的系统压测（QAS-001, QAS-002）中，该架构暴露出两个致命的单点瓶颈：
1. **数据库打宽风险**：面对瞬间激增至 20,000 QPS 的并发读请求，核心数据库的连接池在 3 秒内被彻底耗尽，导致数据库大面积拒绝服务。
2. **外部依赖雪崩**：第三方视频云 API 出现偶发的 2 秒网络延迟时，这种“同步阻塞”设计导致我们自己应用服务器的 Web 线程池被迅速占满，不仅直播进不去，甚至拖垮了其他毫不相关的核心业务。
**因此，本决策在 2026-05-28 被正式废弃，全面演进为引入“多级缓存与断路器”的高可用防御架构（详见替代方案：ADR-002a）。**
