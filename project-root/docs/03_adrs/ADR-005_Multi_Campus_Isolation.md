### ADR-005：多校区数据安全采用“逻辑隔离（Campus_ID 共享表）”架构

---

> **状态:** Accepted
> **日期:** 2026-05-28
> **关联场景:**补充跨校区数据安全隔离场景
> **关联模块：**核心数据访问层 (DAO)
> 
>---

#### 1. 背景 (Context)
根据项目的业务约束，本在线教育平台需要具备服务多校区（如存在不同的合作学校或同一学校有不同校区）的能力。不同校区之间的学生数据、课程版权信息、交易订单财务报表属于高度敏感的隐私数据。系统必须在体系结构层面保证严格的数据隔离，坚决防止校区 A 的教务管理员越权查询到校区 B 的核心数据。与此同时，由于受到“团队规模小、运维及采购预算有限”的客观组织约束，架构方案不能过于臃肿，需要严格控制基础设施的总体持有成本。

#### 2. 决策 (Decision)
在数据架构上采用基于字段的逻辑隔离（Shared Database, Shared Schema with Campus_ID）方案：
* **统一租户标识**：所有与租户/校区相关的数据库表均强制设计一个 `campus_id`（校区唯一标识）字段。
* **数据访问层自动拦截注入**：在系统底层的数据持久化层（DAO 框架），统一配置多租户动态拦截器。
* **无感动态注入**：拦截器解析当前请求上下文中的用户会话 Token，提取其所属的 `campus_id`。在底层的 SQL 解析引擎执行前，自动且强制地在所有查询、修改、删除语句的 `WHERE` 条件中追加 `AND campus_id= :current_campus_id` 条件，从底层统一防御。

#### 3. 备选方案 (Alternatives)
* **方案A：独立数据库隔离**
    * *缺点*：安全级别最高，但硬件成本高昂。随着校区数量的增加，需要维护大量的数据库连接池，使得数据库的版本升级、Schema 结构迁移、全量备份运维工作变得极其沉重，超出小团队的维护极限。
* **方案B：独立部署套件隔离（Silo 孤岛模式）**
    * *缺点*：每个校区完全独立部署一套计算和存储资源，虽然完全物理隔离，但导致版本更新极其困难，且平台无法进行全网跨校区的数据宏观聚合分析。

#### 4. 后果 (Consequences)
* **收益（高开发运维效率与自动化防御）**：所有租户共享一套基础设施和应用代码，部署与维护成本极低，通过底层框架拦截器实现了租户数据隔离对业务代码的零侵入，从根源上消除了开发人员因漏写 `where` 条件而导致的跨校区垂直/水平越权漏洞。
* **代价/权衡（技术债务）**：逻辑隔离存在一定的“嘈杂邻居”风险（如某个校区遭遇大流量，会间接导致共享数据库的 CPU 飙升，拖慢其他校区），必须在后续配套实施物理层的数据库连接池配额与流量限制。

#### 5. 验证计划 (Validation)
* **越权查询自动化测试**：创建一个持有“校区 A（`campus_id = campus_A`）”凭证的模拟用户 Session。调用一个不带任何参数的通用课程列表查询 API。
* **预期结果**：使用 SQL 日志嗅探器捕获底层实际发往 MySQL 的语句，验证其是否被成功修改为 `SELECT ... WHERE campus_id = 'campus_A'`；随后，该 Session 尝试显式传入参数恶意读取属于校区 B 的课程数据，验证数据层是否返回空集（或拦截器主动抛出 HTTP 403 越权异常），确认越权成功率为 0%。
