### ADR-005：多校区数据安全采用“逻辑隔离（Campus_ID 共享表）”架构

---

> **状态:** Accepted
> **日期:** 2026-05-28
> **关联场景:**补充跨校区数据安全隔离场景
> **关联模块：**核心数据访问层 (DAO)
> 
>---

#### 1. 背景 (Context)
根据项目的业务约束，本在线教育平台需要具备服务多校区（如存在不同的合作学校或同一学校有不同校区）的能力。不同校区之间的学生数据、课程版权信息、交易订单财务报表属于高度敏感的隐私数据。系统必须在体系结构层面保证严格的数据隔离，坚决防止校区 A 的教务管理员越权查询到校区 B 的核心数据。与此同时，由于受到“团队规模小、运维及采购预算有限”的客观组织约束，架构方案不能过于臃肿，需要严格控制基础设施的总体持有成本。

#### 2. 决策驱动因素(Factors)
在数据架构上采用基于字段的逻辑隔离（Shared Database, Shared Schema with Campus_ID）方案，因此存在两条约束：
* **约束1**: 数据安全约束坚决防止校区 A 的管理员通过篡改参数水平越权或垂直越权读取校区 B 的核心财务与课程资产。 
* **约束2**: 总体持有成本约束团队技术栈运维能力有限，必须控制多机构扩张时的硬件采购与 Schema 维护成本。

#### 3. 备选方案 (Alternatives)
* **方案A：独立数据库隔离**
    * **描述**: 为每一个合作校区完全独立采购和部署一套专属的数据库实例，数据在物理层完全断绝连接。
    * **优点**: 隔离级别最高，安全性极强，单个校区遭遇大流量不会波及其他校区（零嘈杂邻居风险）。
    * **缺点**: 随着校区数量的增加，硬件开销巨大；跨校区的全局宏观数据统计分析极其困难；多实例的 Schema 迁移升级成本极其高昂。
    * **对质量属性的影响**: 带来了极致的安全性，但严重违背了经济性与可修改性（运维升级难度）的组织约束。
* **方案B: 共享数据库与 Schema，基于 Campus_ID 字段逻辑隔离** 
    * **描述**: 所有校区共享一套数据库集群。在所有涉及空间维度的业务表中强制增设 `campus_id` 字段。在持久化数据访问层统一配置动态多校区拦截器，在 SQL 编译期强制无感注入 `WHERE campus_id = :current_id` 条件。
    * **优点**: 基础设施总体成本极低，版本迭代与结构变更仅需操作一套数据库；通过底层框架拦截器实现了全自动化防御，消除了开发人员漏写条件引发的越权漏洞。
    * **缺点**: 存在“嘈杂邻居”风险，若 A 校区遭遇大规模突发压测，共享数据库的 CPU 飙升会间接拖慢 B 校区的响应。 
    * **对质量属性的影响**: 以极佳的开发效率/可修改性和最低的经济成本满足了安全性红线，但对高负载下的隔离性（可用性）提出了挑战。


#### 4. 决策结果 (Result)

综上，**目前采用方案B对当前环境更有利。**
在项目初期到中期，成本控制和快速迭代是团队生存的关键。方案 B 带来的嘈杂邻居风险，后续可以通过在网关层针对 `campus_id` 实施多租户配额限流来有效对冲。用可控的底层软件设计换取昂贵的硬件物理隔离，是最合理的架构权衡。

#### 5. 后果 (Consequences)
* **正面影响**：平台具备了平滑接入成百上千个合作校区的高吞吐能力，新校区开通仅需在配置表增加一条记录（秒级开通），运维升级成本极低。
* **负面影响/权衡**：应用层的所有复杂 SQL 查询均需经过多校区解析器的二次重写，对极其复杂的跨表多级联会带来轻微的性能损耗。
* **引入的技术债务**： 所有开发人员必须严格遵循 DDD 规范，禁止在非隔离表中混用数据；必须在数据访问层建立完备的多校区动态路由拦截单元测试。

#### 6. 验证计划 (Validation)
* **越权查询自动化测试**：创建一个持有“校区 A（`campus_id = campus_A`）”凭证的模拟用户 Session。调用一个不带任何参数的通用课程列表查询 API。
* **预期结果**：使用 SQL 日志嗅探器捕获底层实际发往 MySQL 的语句，验证其是否被成功修改为 `SELECT ... WHERE campus_id = 'campus_A'`；随后，该 Session 尝试显式传入参数恶意读取属于校区 B 的课程数据，验证数据层是否返回空集（或拦截器主动抛出 HTTP 403 越权异常），确认越权成功率为 0%。 详细验证过程见：[链接到 docs/05_evidence/PoC_Report.md（由于条件限制仅有验证计划暂未实际验证）](../05_evidence/)
