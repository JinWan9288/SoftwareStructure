### ADR-002：进入直播间采用“权益缓存+短期播放令牌+分级限流与熔断”设计

---

> **状态:** Accepted
> **日期:** 2026-05-28
> **关联场景:** QA-P1 (高并发性能), QA-A2 (系统保护)
> **关联模块**: 直播接入服务 
>
> ---

####  **1. 背景（Context）**

开课前 10 分钟，系统将面临高达 20,000 QPS 的进入直播间突发读流量，每次请求都需要校验用户购买权益，并调用第三方视频云 API 获取底层的防盗链推拉流地址。
底层关系型数据库绝对无法承受如此规模的瞬间查询打宽，同时，第三方视频云 API 在高峰期极易发生 2 秒以上的延迟抖动。如果不实施严格的资源隔离与降级策略，外部接口的慢响应会迅速耗尽 Web 应用的线程池，导致平台整体瘫痪以及服务雪崩。

#### 2. 决策 (Decision)
采用多级缓存架构与防御性熔断降级策略：
* **独立入口与两级缓存**：拆分独立的 `Live Access Service`。采用本地 L1 (Caffeine) + 分布式 L2 (Redis, TTL=60s) 查询用户权益，未命中时才回源底层数据库。
* **超时控制与断路器**：对第三方视频云 API 调用设置 200ms 超时阈值，一旦错误率或超时率达到 20%，则触发断路器熔断 60 秒。
* **动态防盗链令牌**：网关利用对称加密生成 5 分钟绝对过期的动态 Token 作为播放凭证下发给客户端，防范资源被恶意抓包盗播。
* **明确的业务降级语义**：熔断期间触发 Fail-fast 机制，接口直接返回 HTTP 429 或“正在排队中”静态文案，明确语义为：“暂不可进入直播间，但不影响已经在直播间内的用户继续观看”。

#### 3. 备选方案 (Alternatives)
* **方案A：每次请求同步查询数据库与视频云 API**
    * *缺点*：违背了高并发设计常识。DB 在 20,000 QPS 下必崩，外部视频云的任何网络微小波动都会通过长连接阻塞导致源站线程池被占满，无法满足 QAS-001 规定的性能指标。
* **方案B：采用长效静态 URL 防盗链**
    * *缺点*：下发固定的拉流地址虽然节省了每次计算 Token 和请求视频云的开销，但无法限制 URL 被恶意分享到外部论坛，严重违背平台安全性（也即防盗播）的底线约束。

#### 4. 后果 (Consequences)
* **收益（高吞吐与防雪崩）**：通过缓存屏障和熔断器，极大提升了入口的吞吐上限并实现了故障隔离，稳定负载下接口 P95 响应可控制在 300ms 内，降级态更是因快速失败缩减至 200ms 内。
* **代价/权衡（一致性妥协）**：权益状态存在短暂不一致现象。例如用户发起退款后，在 Redis 缓存的 60s TTL 失效前，该用户依然可能拿到 Token 进入直播间，经业务侧评估，此极短时间窗口的越权风险对于教育平台可接受。

#### 5. 验证计划 (Validation)
构建小型压测原型验证关键路径容错能力：
* **熔断与降级测试**：在压测环境注入视频云 API 的 Mock 服务。并发压至 10,000 QPS 时，手动开启 Mock 端的 2 秒延迟 + 20% 错误率。
* **验证指标**：确认 `Live Access Service` 能够在 30 秒内成功触发断路器全开，应用服务器未出现线程阻塞导致的 OOM 现象，且降级页面（正在排队中的提示页面）的响应 P95 稳定在 200ms 以内。恢复 Mock 延迟后，验证断路器能通过半开状态自动恢复正常流量。
