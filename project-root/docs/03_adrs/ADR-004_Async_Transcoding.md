### ADR-004：视频转码服务采用“消息队列驱动的异步任务”架构

---

> **状态:** Accepted
> **日期:** 2026-05-28
> **关联场景:** 补充核心点播链路高负载场景 
> **关联模块:** 转码 Worker, OSS
>
> ---

#### 1. 背景 (Context)
- 教师在直播结束后生成的录播文件，或直接上传的预制教学视频，必须经过流媒体转码。转码需要将原始高码率视频切片（HLS/M3U8）并转换为多种分辨率（1080P/720P/360P）以适应不同学生的动态带宽。
- 该任务是极其消耗服务器 CPU/GPU 资源且耗时较长的重型计算任务，如果在 Web 应用的主线程中同步处理、或者通过简单的 HTTP 同步调用转码服务，在多位教师同时下课、集中生成回放的峰值时期，会导致 Web 服务器线程池在几秒内迅速耗尽，引发全局系统雪崩。

#### 2. 决策 (Decision)
将视频转码模块从主业务链路上彻底剥离，**采用基于消息队列驱动的异步分布式任务架构**：
* **事件驱动**：当视频上传成功或直播录制落盘后，核心业务系统向消息队列（RabbitMQ/Kafka）发布一条 `VideoUploadedEvent` 消息（包含视频元数据及唯一任务 ID）。
* **工作线程集群**：部署一组完全无状态、专门用于执行 FFmpeg 转码命令的转码 Worker 节点。
* **拉取式消费与显式确认**：转码 Worker 采用 Pull 模式从队列中获取任务，同一时间一个任务仅由一个 Worker 锁定执行。转码完成后，Worker 将切片文件上传至对象存储（OSS），并向核心业务系统发送完成通知，同时向队列显式响应 ACK。

#### 3. 备选方案 (Alternatives)
* **方案A：基于数据库轮询的定时任务调度**
    * *缺点*：多个 Worker 节点频繁高频轮询数据库的全局任务表，会导致数据库产生严重的读写锁竞争。为了防止重复消费，还必须引入复杂的分布式锁机制，实时响应性差。
* **方案B：Web 服务同步调用远程转码 API**
    * *缺点*：长连接 HTTP 同步等待会导致大量的应用服务器线程处于 Block 状态，极易耗尽系统资源，转码失败时也缺乏原生的重试与削峰缓冲机制。

#### 4. 后果 (Consequences)
* **收益（高吞吐与容错削峰）**：具备完美的流量削峰能力。即使有海量视频在同一时刻产生，任务也只是在消息队列中排队，不会压垮计算集群。由于消息队列具备显式的 ACK 机制，若某个 Worker 在转码中途突然崩溃，队列检测到连接断开会自动将任务重新投递给其他健康的 Worker 节点，确保任务零丢失。
* **代价/权衡（最终一致性）**：转码成为了一个异步过程。前端用户无法立即看到转码后的视频，需要设计状态轮询 API 或 WebSocket 通知机制来动态更新前端视频列表状态。

#### 5. 验证计划 (Validation)
* **宕机重投递测试**：向消息队列连续注入 20 个大视频转码任务。在 Worker-A（随机选取用户） 正在执行其中某个任务的中途，强制杀死 Worker-A 容器进程（模拟崩溃）。
* **预期结果**：核心消息队列正确回收了该未 ACK 的消息，并将其安全地分配给了 Worker-B （另一个不同的随机用户）重新执行，检查最终对象存储中各分辨率的 HLS 切片是否完好，确保转码流程能完全自愈。
