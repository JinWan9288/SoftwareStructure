### ADR-004：视频转码服务采用“消息队列驱动的异步任务”架构

---

> **状态:** Accepted
> **日期:** 2026-05-28
> **关联场景:** 补充核心点播链路高负载场景 
> **关联模块:** 转码 Worker, OSS
>
> ---

#### 1. 背景 (Context)
- 教师在直播结束后生成的录播文件，或直接上传的预制教学视频，必须经过流媒体转码。转码需要将原始高码率视频切片（HLS/M3U8）并转换为多种分辨率（1080P/720P/360P）以适应不同学生的动态带宽。
- 该任务是极其消耗服务器 CPU/GPU 资源且耗时较长的重型计算任务，如果在 Web 应用的主线程中同步处理、或者通过简单的 HTTP 同步调用转码服务，在多位教师同时下课、集中生成回放的峰值时期，会导致 Web 服务器线程池在几秒内迅速耗尽，引发全局系统雪崩。

#### 2. 决策驱动因素(Factors)
将视频转码模块从主业务链路上彻底剥离，**采用基于消息队列驱动的异步分布式任务架构**，因此存在两条约束：
*  **约束1**: 避免 CPU 密集型的重型计算负载反向吞噬和拖垮 C 端核心看播与下单主链路。 
* **约束2**: 需支持媒体文件转码的强容错性，转码节点突发宕机时任务不可丢失。

#### 3. 备选方案 (Alternatives)
* **方案A: 业务层直接同步调用转码服务 API** 
    * **描述**: 当视频上传成功后，核心业务系统发起长连接 HTTP 请求，同步等待转码服务器执行 FFmpeg 命令并返回结果。
    * **优点**: 代码调用逻辑简单，核心系统可以实时获知转码结果并更新数据库状态。
    * **缺点**: 转码动辄消耗数分钟乃至数小时，长连接会导致大量的 Web 服务器线程进入阻塞状态，突发集中上传时必崩。
    * **对质量属性的影响**: 数据及时性较高，但对核心主链路的性能与可用性具有毁灭性打击。 

* **方案B: 消息队列驱动的分布式异步任务 Worker 架构**
    * **描述**: 视频上传落盘后，核心系统向消息队列发布一条 `VideoUploadedEvent`，随后立即返回。部署一组独立的无状态转码 Worker 节点，采用 Pull 模式异步消费并执行分布式转码。 
    * **优点**: 具备极佳的流量削峰能力，任务堆积在 MQ 中排队，不会压垮计算集群，并且Worker 节点可根据排队情况动态横向扩容（HPA）。 
    * **缺点**: 转码过程成为纯异步化，前端用户无法立即看到回放，存在可见性延迟。 
    * **对质量属性的影响**: 完美保障了核心主链路的可用性与隔离性，但适度妥协了转码视频的即时可见性。


#### 4. 决策结果 (Result)

综上，**目前采用方案B对当前环境更有利。**
视频转码天然属于非即时性任务。采用异步事件驱动架构，不仅彻底解耦了重型计算对 Web 服务的资源占用，还利用消息队列原生的重试与 ACK 机制，天然获得了高容错能力。

#### 5. 后果 (Consequences)
* **正面影响**：视频上传与转码成功实现了 100% 的流量削峰与故障隔离，即使转码集群全部瘫痪，也绝不影响学生的正常看播与下单选课。
*  **负面影响/权衡**：业务链路由同步变异步，增加了系统的复杂性，需要专门开发转码状态查询 API 以及支持前端异步状态刷新的 WebSocket 或轮询机制。
* **引入的技术债务**：需要部署并维护独立的 FFmpeg 分布式计算节点，需要配置完备的消息持久化机制以及应对转码失败任务的死信队列。

#### 6. 验证计划 (Validation)
* **宕机重投递测试**：向消息队列连续注入 20 个大视频转码任务。在 Worker-A（随机选取用户） 正在执行其中某个任务的中途，强制杀死 Worker-A 容器进程（模拟崩溃）。
* **预期结果**：核心消息队列正确回收了该未 ACK 的消息，并将其安全地分配给了 Worker-B （另一个不同的随机用户）重新执行，检查最终对象存储中各分辨率的 HLS 切片是否完好，确保转码流程能完全自愈。详细验证过程见：[链接到 docs/05_evidence/PoC_Report.md（由于条件限制仅有验证计划暂未实际验证）](../05_evidence/)
