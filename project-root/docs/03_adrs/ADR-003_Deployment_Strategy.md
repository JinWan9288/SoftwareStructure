### ADR-003: 部署策略采用“源站集群调度与第三方 CDN 边缘节点分发”架构

---

> **状态:** Accepted 
> **日期:** 2026-05-28
> **关联场景:**QAS-001 (进入直播间洪峰) 
> **关联模块:** 源站集群, CDN 边缘节点
>
> ---

#### 1. 背景 (Context)
本系统需要支撑开学季单场 10,000 名学生同时在线观看直播（QAS-001），且画面必须流畅不卡顿。音视频流媒体分发属于极其消耗网络带宽和网络 I/O 资源的重型业务。如果所有学生的拉流请求全部直接涌向平台的中心源站服务器，不仅单机带宽会瞬间被拉满导致网络瘫痪，而且由于地理位置和网络运营商的差异，远端用户会遭遇严重的网络延迟与高卡顿率。在团队运维能力和物理服务器预算有限的组织约束下，系统必须具备平滑的横向扩展能力，且单点故障不能导致大面积断播。

#### 2. 决策驱动因素(Factors)

当大量学生同时进入直播间时，我们需要关注的驱动因素如下：

-  **QAS-001**:大规模在线看播保障万人同时看播时画面流畅、不发生物理断流。
-  **约束**: 中心源站的 BGP 带宽成本极其昂贵，团队缺乏全球多机房运维与智能网络调度的核心能力。

#### 3. 备选方案 (Alternatives)
* **方案A: 纯中心云服务器集群化分发**
    - **描述**: 向云厂商购买高带宽独享网络，完全通过中心源站部署的流媒体集群进行媒体流切片与高并发下发。 
    - **优点**: 流媒体链路完全内控，防盗链鉴权极为简单，无需跨厂商同步状态。
    -  **缺点**: 公网带宽采购成本呈指数级上升，且无法解决物理层面的跨网、跨地域传输延迟痛点。
    - **对质量属性的影响**: 提升了系统的安全性，但严重损害了经济性（成本约束）与高并发下的性能（卡顿率）。 

* **方案B: 源站集群调度与第三方 CDN 边缘节点分发**
    *  **描述**: 中心源站仅负责接收教师端推流、流媒体切片及核心鉴权，将巨大的 C 端拉流带宽卸载到成熟的第三方 CDN 厂商，利用其全国边缘节点进行就近分发。
    * **优点**: 彻底剥离了重型网络 I/O 压力，单场万人直播的流量由 CDN 分担，源站负载极低；学生拉流延迟大幅下降。
    * **缺点**: 带来了对第三方服务商的强依赖，且内容防盗链校验必须外包移动到 CDN 边缘节点执行。
    * **对质量属性的影响**: 实现了极致的伸缩性与低卡顿性能，但略微增加了系统安全性设计的复杂度。

#### 4. 决策结果 (Result)

综上，**目前采用方案B对当前环境更有利。**
流媒体业务的物理定律决定了必须采用边缘分发，小团队自建流媒体分发网络从成本和技术上均不可行，通过采用成熟的 CDN 外包架构，能以最低的财务成本和研发周期换取万人并发下的流畅看播体验。

#### 5. 后果 (Consequences)
* **正面影响**：源站集群出口带宽压力降低 95% 以上，全国各省份学生的看播延迟普遍控制在 2 秒以内，卡顿率降至 1% 以下。
* **负面影响/权衡**： 平台引入了第三方 CDN 服务商的黑盒依赖，若 CDN 厂商节点遭遇骨干网故障，平台需要具备快速切换备用 CDN 的能力。
* **引入的技术债务** ：必须实现一套跨平台的动态 URL 签名生成算法，并与 CDN 厂商同步共享加密私钥，并且需要在客户端 SDK 内置多 CDN 级联调度与断线自动重连逻辑。

#### 6. 验证计划 (Validation)
* **节点断流切换验证**：在测试环境中，模拟学生正在从 A 边缘节点拉取 HTTP-FLV 流，随后运维人员手动将该节点流量掐断（模拟节点宕机）。
* **预期结果**：验证学生端播放器是否能在 5 秒内自动通过内部 SDK 切换到预设的 B 备用节点 URL 并恢复画面，并且整个切换过程中系统未向用户抛出彻底断播的异常错误。详细验证过程见：[链接到 docs/05_evidence/PoC_Report.md（由于条件限制仅有验证计划暂未实际验证）](../05_evidence/)
