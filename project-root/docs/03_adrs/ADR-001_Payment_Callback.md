## ADR-001：支付回调采用“同步 RPC 强一致调用”

---

> **状态:** Deprecated (已被 ADR-001a 替代) 
> **日期:**  2025-11-10 
> **关联场景:** -
> **关联模块**: 订单服务, 权益服务  
>
> ---

#### **1. 背景（Context）**

在项目初期（MVP 阶段），为了追求最快的开发速度与最直观的代码逻辑，我们需要实现用户支付成功后的权益发放。由于当时系统预估并发量较低，团队决定采用最简单的同步调用模式。

#### 2. 决策 (Decision)
订单服务在接收到第三方支付网关的回调后，在同一个 HTTP 请求线程内，直接通过 RPC/REST 同步调用权益服务的 API。只有当权益服务返回“发放成功”后，订单服务才向第三方支付平台返回 HTTP 200 成功响应。

#### 3. 后果 (Consequences)
* **收益**：开发极其简单，不需要引入消息队列等中间件，没有分布式事务的数据不一致问题（所见即所得）。
* **代价**：订单服务与权益服务在时间与空间上强耦合。

#### 4. 废弃原因 (Reason)
在后续针对“开学季万人并发”的压测（QAS-003）中，该架构暴露出严重的**级联故障（Cascading Failures）风险**。当并发回调达到 5,000 QPS 时，如果权益服务因高负载产生 1 秒的延迟，将直接导致订单服务的 Web 线程池在几秒内被全部耗尽，进而触发支付网关的不断重试，造成雪崩。
**因此，本决策在 2026-05-28 被废弃，全面演进为基于消息队列的异步最终一致性架构（详见 ADR-001a）。**
