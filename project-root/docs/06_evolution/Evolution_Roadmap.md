# Evolution_Roadmap

## 1. 当前架构版本 (v1.0) 现状与局限
当前的 `v1.0` 架构通过引入多级缓存、消息队列削峰、服务降级与第三方 CDN 分发，成功达成了保障开学季万人同时在线直播的核心目标。
**局限性**:
1. **数据一致性妥协较多**: 支付链路依赖简单的 MQ 发布，缺乏应对 MQ 宕机时的“本地消息表(Outbox)”机制。
2. **交互延迟受限于协议**: 直播底层的拉流协议目前使用 HTTP-FLV/HLS，端到端延迟仍在 2~5 秒之间，无法满足未来更高级别的“连麦互动”需求。
3. **多校区扩展性差**: `campus_id` 的逻辑隔离在校区激增时，将面临“嘈杂邻居”导致的数据库物理瓶颈。

## 2. 演进触发条件
- **业务层面**: 当平台推出“1V1 沉浸式辅导”或“多端超低延迟连麦答题”业务时。
- **规模层面**: 当合作校区超过 100 个，单一 MySQL 集群无法承受复杂的跨表多校区聚合报表查询时。

## 3. 演进路线图

### v1.0 -> v1.1 (短期演进, 3~6个月)
- **目标**: 消除数据丢失风险，加固平台可用性底座。
- **关键变更**:
  1. **引入 Outbox Pattern (发件箱模式)**: 在 Order Service 中实现订单状态更新与事件插入的本地事务，结合 Debezium (CDC) 或定时轮询投递到 MQ，彻底还清一致性技术债。
  2. **细化重试与死信队列 (DLQ) 治理**: 为所有核心 MQ 消费者建立统一的补偿看板。
- **偿还的技术债务**: TD-001, TD-004。

### v1.1 -> v2.0 (中期演进, 6~12个月)
- **目标**: 实现超低延迟互动与跨地域高可用。
- **关键架构变更**:
  1. **流媒体协议升级**: 引入 WebRTC 技术栈替代 HTTP-FLV，将端到端视频延迟从 3s 压缩至 500ms 以内。
  2. **数据架构升级**: 针对多校区报表查询，引入 ClickHouse 或 Doris 作为 OLAP 引擎，将核心 MySQL 数据通过 CDC 同步至数仓，实现 TP 与 AP 物理隔离。
- **迁移策略**: WebRTC 采用“双轨并行”灰度策略，旧版本 App 继续使用 FLV，新版本 App 尝试 WebRTC，通过下发不同的 PlayToken 路由。

### v2.0 -> v3.0 (长期愿景)
- **目标**: 智能化与云原生 Serverless 架构。
- **关键演进**:
  1. **转码切片 Serverless 化**: 将重度消耗计算资源的 FFmpeg Worker 迁移至云厂商的 Serverless 容器服务 (如 AWS Fargate / 阿里云 ECI)，按转码任务时长计费，极致降本。
  2. **AI 驱动**: 引入大语言模型 (LLM)，基于收集到的学习进度与错题数据，动态生成个性化复习大纲。

## 4. 演进中的架构原则
- **高可用优先**: 任何演进不得牺牲核心交易与直播链路的容错能力。
- **无状态设计**: 所有新增的 Web 和 Worker 服务必须保持绝对无状态，支持随时横向伸缩。
- **演进式替换**: 涉及核心域（如订单、流媒体）的改造，必须支持金丝雀发布和秒级回滚。
