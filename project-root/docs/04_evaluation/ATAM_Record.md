# ATAM_Record

## 1. 评估范围与目标

本文件记录对“在线教育直播与点播平台”的轻量级 ATAM 架构评估结果。评估范围覆盖 Phase 1 中识别的架构驱动因素与质量属性场景、Phase 2 中形成的 C4 架构视图，以及 Phase 3 之前已经接受或废弃的 ADR。

本次评估重点关注以下问题：

- 架构是否能够支撑单场万人直播与开课前高峰进入直播间。
- 支付回调、课程权益发放、学习进度上报等异步链路是否具备足够的可用性和一致性保障。
- 第三方视频云、CDN、支付平台等外部依赖异常时，系统是否具备隔离、熔断和降级能力。
- 点播和直播资源是否具备必要的防盗链与短期 Token 鉴权机制。
- 当前架构中哪些设计属于敏感点、权衡点、风险或技术债。

## 2. 业务驱动因素回顾

根据 `docs/01_adf/ADF_Brief.md`，系统的核心业务目标是为在线教育公司构建支持万人同时在线的高可用直播与点播平台，覆盖课程浏览、课程购买、直播上课、点播回看、弹幕互动和学习数据采集。

主要业务驱动因素如下：

- **高并发直播体验**: 开学季或集中开课前，学生需要在短时间内进入直播间，单场直播需要支撑 10,000 人同时观看，端到端视频延迟目标为不超过 3 秒。
- **交易闭环可靠性**: 学生支付成功后应可靠获得课程权益，支付平台的重复回调或延迟回调不能造成重复发放、漏发或订单状态错误。
- **付费内容安全**: 点播与直播资源属于平台核心资产，需要通过短期 Token、签名 URL 和 CDN 边缘校验降低盗播风险。
- **外部依赖可控**: 视频云、支付平台和 CDN 均为外部系统，架构必须承认外部系统的不可控性，并通过缓存、熔断、异步化和降级降低影响范围。
- **小团队可维护性**: 团队运维能力有限，不适合引入过重的分布式事务、私有 CDN 或复杂 DRM，需要在质量属性和实现复杂度之间做折中。

## 5. 架构方法分析

### 5.1 ADR-001a：支付核心链路采用异步事件驱动、最终一致与对账补偿

该决策主要响应 QAS-004。支付平台回调具有至少一次投递语义，因此 Order Service 使用 `paymentOrderId` 唯一键进行订单侧幂等拦截，首次回调推进订单状态并发布 `OrderPaidEvent`，Entitlement Service 再以 `userId + courseId` 做权益侧二次幂等。

该方法的正向效果是避免订单服务在回调线程中同步等待权益服务，降低级联故障风险，并通过 MQ 实现削峰和最终一致。主要代价是用户支付后可能出现短暂“权益确认中”的窗口，因此需要前端提示、补偿任务和审计日志共同支撑。

### 5.2 ADR-002a：进入直播间采用权益缓存、短期播放令牌、限流与熔断

该决策主要响应 QAS-001 和 QAS-003，并间接支撑 QAS-005、QAS-006。Live Access Service 使用 L1 Caffeine 缓存和 L2 Redis 缓存降低 MySQL 压力，缓存未命中时才回源数据库；对第三方视频云 API 设置 200ms 超时与 CircuitBreaker 熔断；同时签发短期 PlayToken。

该方法显著提升直播入口吞吐量，并将视频云抖动限制在 Live Access Service 内部。主要代价是权益缓存 TTL 带来短暂一致性窗口，且熔断阈值、缓存 TTL 和限流策略都成为敏感配置，需要压测和运行期监控持续校准。

### 5.3 ADR-003：源站集群调度与第三方 CDN 边缘节点分发

该决策主要响应 QAS-001。学生端 HTTP-FLV/HLS 拉流不直接打到平台中心服务，而是访问第三方 CDN 边缘节点，平台侧只负责业务鉴权和签名 URL 下发。

该方法把最重的网络出口流量从中心平台卸载到 CDN，能够支撑万人直播观看并降低跨地域卡顿。主要代价是引入第三方 CDN 强依赖，防盗链校验必须在边缘完成，CDN 配置、回源策略和节点质量成为影响用户体验的重要敏感点。

### 5.4 ADR-004：视频转码服务采用消息队列驱动的异步任务

该决策支撑点播转码链路和系统整体可用性。视频上传或直播录制完成后发布 `VideoUploadedEvent`，Transcode Worker 从 MQ 拉取任务，使用 FFmpeg 转码并上传对象存储。

该方法把 CPU/GPU 密集型转码任务从 Web 主链路剥离，避免同步转码拖垮业务线程池。主要代价是转码结果具备最终一致性，前端需要轮询或通知机制展示“转码中/可播放/失败”等状态。

### 5.5 ADR-005：多校区数据安全采用 campus_id 逻辑隔离

该决策支撑多校区数据安全和小团队运维约束。系统在共享数据库和共享 Schema 中通过 `campus_id` 字段进行逻辑隔离，并由 DAO 层拦截器自动注入校区过滤条件。

该方法降低多校区部署和运维成本，也减少业务代码漏写过滤条件的风险。主要代价是不同校区共享数据库资源，存在嘈杂邻居风险；一旦 DAO 拦截器配置错误，可能影响数据隔离效果，因此该点属于重要安全敏感点。

### 5.6 ADR-006：付费课程资源采用时间戳防盗链与短期动态 Token 鉴权

该决策主要响应 QAS-005，并配合 ADR-003 在 CDN 边缘执行校验。Media Auth Service 生成包含用户、课程、IP 和时间戳的签名 URL，CDN 根据 `auth_key` 校验合法性，非法请求直接返回 HTTP 403。

该方法兼顾性能和安全，不需要每个切片请求都回源鉴权。主要代价是强依赖源站与 CDN 的时间同步，也需要妥善管理签名密钥轮换、TTL 长度和客户端 IP 变化场景。

### 5.7 QAS-002：课程详情高频浏览的视图级方案

QAS-002 当前没有单独 ADR，但在 View-002 和 View-009 中由 Course Service、Redis 热点缓存和数据库读压力隔离承担。该方案能够降低课程详情高频浏览对 MySQL 的冲击。

该方法的主要敏感点是热点缓存命中率、缓存过期策略和数据库回源限流。如果营销活动导致缓存穿透或热点 Key 失效，需要额外的缓存预热、互斥回源和限流策略支撑。

### 5.8 QAS-007：交互功能热更新的视图级方案

QAS-007 当前没有单独 ADR，但在 View-002 和 View-009 中由 Barrage Service 独立部署、多副本和滚动发布承担。弹幕和互动服务通过 WebSocket 与前端交互，不阻塞直播拉流主链路。

该方法使互动功能可以相对独立演进，核心交易和拉流链路不需要随互动模块同步发布。主要代价是 WebSocket 长连接在滚动发布期间需要优雅摘流、连接迁移或前端重连策略，否则会影响互动体验。

### 5.9 QAS-008：学习进度大吞吐量的视图级方案

QAS-008 当前没有单独 ADR，但在 View-002、View-008 和 View-009 中由 Learning Record Service、MQ、Progress Aggregation Worker 和 MySQL 批量落库承担。入口服务写入 MQ 后快速返回，后台 Worker 按 `userId + courseId` 聚合并批量 UPSERT。

该方法能把高频小写转换成低频批量写，降低数据库写锁争用。主要代价是学习进度具有最终一致性，且 MQ Lag、Worker 扩容策略和重复事件去重都会影响最终数据准确性。

| SP-005 | MQ 积压、重试和死信策略影响支付权益、学习进度和转码任务的最终一致性。 | 可用性、一致性、性能 | Message Queue、Entitlement Service、Learning Worker、Transcode Worker |

## 7. 权衡点清单

完整权衡点分析见 `docs/04_evaluation/Sensitivity_Tradeoff.md`。

| ID | 描述 | 正向影响 | 负向影响 |
|---|---|---|---|
| TP-001 | 使用缓存保护直播入口权益查询。 | 提升性能，降低数据库压力。 | 带来最长约 TTL 时间的一致性窗口。 |
| TP-002 | 使用 MQ 异步发放支付权益。 | 隔离支付回调与权益服务，提升可用性。 | 用户支付成功后权益可能短暂延迟生效。 |
| TP-003 | 使用第三方 CDN 分发直播和点播流。 | 卸载中心带宽，改善跨地域播放体验。 | 引入 CDN 强依赖和边缘防盗链配置复杂度。 |
| TP-004 | 使用短期 Token 防盗链而非 DRM。 | 性能开销低，适合课程项目和普通付费内容。 | 无法防录屏，依赖时间同步和密钥管理。 |
| TP-005 | 使用 `campus_id` 逻辑隔离而非独立数据库。 | 降低部署和运维成本，便于统一升级。 | 存在嘈杂邻居和拦截器漏配风险。 |
| TP-006 | 学习进度使用 MQ 和窗口聚合。 | 提升写入吞吐，降低数据库锁竞争。 | 进度数据存在最终一致延迟。 |
