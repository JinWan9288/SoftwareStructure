## 架构驱动因素简报 (ADF Brief)

**1.项目概述**

- 本系统旨在为某在线教育公司构建一个支持万人同时在线的高可用教育直播与点播平台，支持课程购买、点播学习与直播上课入口 。核心目标是在开学季等开课高峰期值场景下，保障单场万人直播的极低延迟与稳定观看体验，且所有付费内容的访问安全可控，最终实现教与学的高效连接 。
- 核心用户角色包括：**教师**（发布课程与作业、查看学生学习情况、直播上课）、**学生**（学习浏览课程、购买课程、进入直播间互动与点播回看）、**管理员**（上架课程、查看订单流转、数据管理）。
- 系统边界**范围内**包含课程购买链路（订单状态机）、学生权益管理、直播接入网关（重点是分发鉴权令牌与房间信息）、点播鉴权逻辑（防盗链点播）。**不包含**视频流的底层推送与拉取网络（依赖第三方视频云）、底层转码存储能力（同样依赖视频云）、资金的实际扣款网关（依赖第三方支付平台）。

**2.功能性需求摘要**

教师这一角色主要有三个功能性需求：
首先，教师需要在开课前能够配置课程大纲并流畅开启直播间，以确保学生能够准时看到上课链接并获取合法的接入凭证。
其次，该角色需要在授课过程中拥有基础的课堂控制权（如签到签退、禁言、发布互动通知等操作），以确保高并发网络环境下的教学秩序。
最后，该角色需要在课后能够查看学生进入直播间的考勤报表以及点播视频的详细观看时长统计，根据这些数据评估学生的异步学习效果。

学生这一角色主要有两个功能性需求：
首先，学生需要在开课前五分钟顺利进入直播间并在观看直播时能够发送实时弹幕，以确保每名学生都能够获取拉流鉴权令牌与老师和其他同学进行实时互动。
最后，该角色需要在下单支付成功后立刻获得课程访问权，要确保该角色随后可无缝进行点播或进入直播。

对于管理员这一角色，该角色的需求是要能够正确配置付费课程的访问权限与防盗链规则，以确保能够保护平台的知识产权与收益。

此外，**四个架构重要需求（ASR）为：**系统需要支撑单场1万并发观看，且端到端视频延迟 ≤ 3s；弹幕系统必须能承受单直播间瞬时上行 2,000 QPS 的写入，且端到端投递延迟 P99 ≤ 500ms，极端洪峰下允许采取限流丢弃策略，但绝不允许阻塞视频流主链路；点播与直播的鉴权必须严格防盗刷；支付回调必须具备幂等性。

**3.质量属性优先级排序**

根据 MoSCoW 方法，核心质量属性优先级如下 ：
**性能与可伸缩性 (Must Have):** 优先级最高，应对开课前高峰值，单场1万并发下延迟 ≤ 3s。
**可用性 (Must Have):** 优先级极高，外部依赖（视频云、第三方支付）发生网络抖动或限流时，核心业务系统绝不能发生雪崩。
**安全性 (Must Have):** 优先级高，所有付费内容的点播与直播拉流必须进行严格鉴权，防盗用且可审计。
**可演进性 (Should Have):** 优先级中等，在不影响直播链路及其余链路的前提下，未来热更新互动功能模块（如投票、问答）。

**4. 约束条件**

**技术约束:** 视频播放、推拉流与底层分发必须强依赖第三方视频云的 API；支付链路必须依赖第三方支付平台的异步回调机制（回调语义与时序不可控）。
**业务约束:** 平台数据涉及学生隐私与交易信息，所有业务日志必须进行数据脱敏，并强制保留关键操作的审计记录。
**组织约束:** 团队的运维能力和人数有限，不适合引入过于复杂的分布式事务框架，需要尽量简单的高可用部署与可观测方案。

**5. 关键干系人及其关注点**

| **干系人角色**  | **主要关注点**                                               | **对应质量属性** |
| --------------- | ------------------------------------------------------------ | ---------------- |
| **学生及教师**  | 选课支付画面流畅，高峰期准时进入直播不卡顿卡死，互动无延迟   | 性能、可用性     |
| **业务 运营方** | 付费内容坚决防盗播，订单状态机绝不出错                       | 安全性、可用性   |
| **系统运维**    | 流量洪峰来临时需要平滑扩容，第三方 API 故障时不压垮平台，出现瓶颈故障时能迅速定位排查 | 可用性、可观测性 |
